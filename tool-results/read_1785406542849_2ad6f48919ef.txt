     1→     1→# Skill: Global Maritime Data Governance & Privacy Swarm
     2→     2→
     3→     3→## Overview
     4→     4→
     5→     5→Autonomous regulatory compliance agent swarm for global maritime freight operations. The swarm automates GDPR/PII anonymisation, EDI compliance auditing, remediation policy generation, and MTTR telemetry tracking across five international jurisdictions. Designed to evolve with emerging regulations, expanding data repositories, satellite AIS feeds, and the unique challenges of extreme weather and special maritime regions.
     6→     6→
     7→     7→## When to Use This Skill
     8→     8→
     9→     9→- Building compliance automation for maritime logistics, shipping, or freight forwarding
    10→    10→- Implementing PII anonymisation pipelines for Bills of Lading, manifests, or customs declarations
    11→    11→- Auditing EDI connections (EDIFACT, ANSI X12, BAPLIE, VGM) for encryption and format compliance
    12→    12→- Generating automated remediation policies from audit findings
    13→    13→- Tracking Mean Time To Remediate (MTTR) for compliance incidents
    14→    14→- Multi-jurisdiction data governance (GDPR, CCPA, LGPD, PDPA, PIPA)
    15→    15→- Weather-aware compliance operations in extreme maritime environments
    16→    16→- Integrating compliance across diverse maritime data repositories (AIS, PCS, IoT, blockchain eBL)
    17→    17→- Satellite-based vessel tracking compliance and route deviation detection
    18→    18→- Carbon emissions reporting compliance (EU ETS, IMO DCS, MRV)

    25→    25→
    26→    26→### 1. Manifest PII Anonymiser (Python)
    27→    27→
    28→    28→- **HMAC-SHA256 deterministic tokenisation** — produces consistent tokens for the same input across runs, enabling cross-referencing without exposing original data
    29→    29→- **Fernet symmetric encryption** — reversible pseudonymisation for customs DPA-covered use cases (AES-128-CBC + HMAC-SHA256)
    30→    30→- **Multi-jurisdiction PII rules** — 7 default rules covering consignee identity, shipper identity, contact info, government IDs, and financial IDs
    31→    31→- **Free-text PII scanning** — regex-based detection of emails, phone numbers, passport numbers, and tax IDs embedded in free-text fields
    32→    32→- **ML NER detection** — spaCy-based named entity recognition for PII in unstructured free-text (remarks, special instructions, hazmat descriptions)
    33→    33→- **Six masking actions** — tokenise, redact, generalise (date granularity), pseudonymise, encrypt, truncate
    34→    34→- **Token format** — `{PREFIX}_{CATEGORY}_{HMAC_TRUNCATED}` (e.g., `MTS_CONS_a3f8c1e9b2d4`)
    35→    35→
    36→    36→### 2. Logistics EDI SQL Auditor (Python)
    37→    37→
    38→    38→- **11 parametric SQL audit queries** across 5 compliance domains
    39→    39→- **Domain: Encryption** (3 queries) — unencrypted EDI transmissions, FTP file transfers, expired TLS certificates
    40→    40→- **Domain: Customs Documentation** (3 queries) — missing customs declarations, missing VGM, expiring dangerous goods docs
    41→    41→- **Domain: EDI Format** (2 queries) — failed validation messages, orphaned references
    42→    42→- **Domain: Data Retention** (2 queries) — PII past retention period, unanonymised historical manifests
    43→    43→- **Domain: Access Control** (1 query) — excessive user permissions
    44→    44→- **Pluggable query registry** — database-backed, versioned queries updatable via API without redeployment
    45→    45→- **Finding persistence** — all results stored as `AuditFinding` records with severity, risk category, and evidence samples
    46→    46→- **EDI profile scanning** — checks each partner connection for encryption status and TLS version
    47→    47→
    48→    48→### 3. Remediation Route Generator (Python)
    49→    49→
    50→    50→- **Decision matrix** — maps 7 risk categories to recommended policy actions automatically
    51→    51→- **Three execution modes** — dry-run (propose only), staged (persist as disabled), apply (persist and enable)
    52→    52→- **Field category inference** — infers PII category from field names when evidence is ambiguous
    53→    53→- **EDI profile updater** — enforces TLS 1.3 and enables encryption on non-compliant partner connections
    54→    54→- **Finding status tracking** — marks findings as in-progress or remediated when policies are generated
    55→    55→
    56→    56→### 4. Telemetry MTTR Tracker (Golang)
    57→    57→
    58→    58→- **Buffered event ingestion** — in-memory buffer with configurable flush interval (default 10s)
    59→    59→- **Background goroutine** — non-blocking writes to the database
    60→    60→- **Ten lifecycle phases** — aligned with Python FindingState: identified, triaged, assigned, in_progress, awaiting_verification, resolved, verified, escalated, risk_accepted, closed, false_positive
    61→    61→- **MTTR calculation** — average and P95 metrics, broken down by severity and risk category; accepts both "resolved" and "verified" as MTTR end points
    62→    62→- **SQLite (dev) / PostgreSQL (prod)** — driver-agnostic via configuration swap
    63→    63→- **HTTP API** — 6 endpoints including `/api/v1/events/sm` for receiving state machine transition payloads
    64→    64→- **Phase mapping** — `FindingStateToPhase` map translates all 10 Python FindingState values to Go EventPhase constants
    65→    65→
    66→    66→### 5. Finding State Machine (Python)
    67→    67→
    68→    68→- **10 states** — DETECTED, TRIAGED, ASSIGNED, IN_REMEDIATION, AWAITING_VERIFICATION, VERIFIED, CLOSED, ESCALATED, RISK_ACCEPTED, FALSE_POSITIVE
    69→    69→- **20 transitions** — each with trigger, actor, guard conditions, timeout rules, and context payloads
    70→    70→- **7 trigger types** — manual_triage, manual_assign, remediation_submitted, verification_passed, verification_failed, auto_escalate_timeout, manual_close, risk_accept, mark_false_positive
    71→    71→- **Guard conditions** — e.g., CLOSURE requires no open remediation tasks; ESCALATION requires sign-off for CRITICAL findings
    72→    72→- **Timeout SLAs** — per-severity auto-escalation (CRITICAL: 1h detected/triaged, 4h assigned, 8h remediation; HIGH: 4h/8h/24h; MEDIUM: 24h/48h/72h)
    73→    73→- **Callback bridge** — registered callback on every successful transition auto-emits FINDING_STATE_CHANGED event to the event bus
    74→    74→- **Go MTTR bridge** — async HTTP POST forwards every transition to Go service via `map_go_phase()` static method
    75→    75→- **Full audit trail** — every transition persisted to `finding_transitions` table with before/after state, trigger, actor, context payload, and auto-escalation flag
    76→    76→- **Manual timeout check** — `POST /api/v1/state-machine/timeout-check` endpoint scans all open findings and auto-escalates SLA breaches
    77→    77→
    78→    78→### 6. Event Bus (Python)
    79→    79→
    80→    80→- **Database-backed event store** — all events persisted to `event_log` table with full metadata
    81→    81→- **PG LISTEN/NOTIFY fallback** — uses PostgreSQL real-time notifications when available; falls back to in-process queue for SQLite
    82→    82→- **Background consumer loop** — processes queued events and dispatches to subscribers
    83→    83→- **Subscriber API** — register handlers for specific event types with optional correlation ID filtering
    84→    84→- **Statistics endpoint** — `GET /api/v1/events/stats` returns total events, processed count, queue depth, transport type, subscriber count
    85→    85→- **Event log query** — `GET /api/v1/events` returns recent events with filtering
    86→    86→- **Manual publish** — `POST /api/v1/events/publish` for testing and external integration
    87→    87→
    88→    88→### 7. Reaction Engine (Python)
    89→    89→
    90→    90→- **7 built-in reaction rules** with conditions and actions:
    91→    91→  1. `react_critical_notification` — CRITICAL findings trigger EDI partner notification and auto-escalation
    92→    92→  2. `react_pii_auto_scan` — PII exposure findings trigger automatic anonymisation scan
    93→    93→  3. `react_cert_expiry_check` — certificate expiry findings trigger compliance audit re-run
    94→    94→  4. `react_timeout_escalation` — timeout events trigger escalation with SLA context
    95→    95→  5. `react_remediation_verification` — remediation completion triggers verification workflow
    96→    96→  6. `react_audit_summary` — audit completion triggers summary report generation
    97→    97→  7. `react_mttr_baseline` — new finding creation triggers MTTR baseline establishment
    98→    98→- **Conditional execution** — each rule evaluates event type, severity, risk category, and payload fields before firing
    99→    99→- **Toggle API** — `PUT /api/v1/reactions/rules/{rule_id}/toggle` enables or disables individual rules at runtime
   100→   100→- **Statistics endpoint** — `GET /api/v1/reactions/stats` returns enabled count, total actions executed, and per-rule action counts
   101→   101→- **Reaction log** — `GET /api/v1/reactions/log` shows recent reaction activity with full context

   103→   103→### 8. Composite Risk Scoring Engine (Python) ★ NEW in v3.0
   104→   104→
   105→   105→- **5-dimensional weighted model** — CRS = 0.30*S_sev + 0.20*S_jur + 0.20*S_sens + 0.15*S_exp + 0.15*S_urg
   106→   106→- **Severity sub-score** — direct lookup (CRITICAL=1.0, HIGH=0.8, MEDIUM=0.5, LOW=0.3, INFO=0.1)
   107→   107→- **Jurisdiction sub-score** — enforcement rigour weighting (GDPR=1.0, CCPA=0.85, LGPD=0.70, PIPA=0.65, PDPA=0.50)
   108→   108→- **Data sensitivity sub-score** — 8 levels from special_category=1.0 to operational=0.25
   109→   109→- **Exposure breadth sub-score** — logarithmic scaling combining record count, partner count, and jurisdiction count
   110→   110→- **Temporal urgency sub-score** — age-based ramping (0-72h), SLA deadline proximity, state-dependent reduction
   111→   111→- **Risk level mapping** — CRS >= 0.80 CRITICAL, >= 0.60 HIGH, >= 0.40 MEDIUM, >= 0.20 LOW, < 0.20 INFO
   112→   112→- **ORM convenience** — `score_finding(audit_finding)` method for direct scoring from database objects

   497→   497→## Security Considerations
   498→   498→
   499→   499→- **HMAC key** — drives all tokenisation determinism; rotating it invalidates every token. Treat as a root CA key.
   500→   500→- **Fernet keys** — generated per-session by default; for production, rotate via a key management service.
   501→   501→- **Gateway auth** — JWT/API key middleware available in pipeline (enable via SwarmConfig for production).
   502→   502→- **CORS** — currently wildcard; lock to your frontend domain in production.
   503→   503→- **Rate limiting** — token-bucket middleware (100 req/60s, 150 burst); production should use Redis-backed distributed limiting.
   504→   504→- **Audit logging** — structured audit log middleware in pipeline captures every request with request ID, user, timestamp, and response status.
