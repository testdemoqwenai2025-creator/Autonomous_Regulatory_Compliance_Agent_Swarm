     1→# Maritime Global Compliance Swarm
     2→
     3→> Autonomous regulatory compliance agent swarm for global maritime freight. Automates GDPR/PII anonymisation, EDI compliance audits, remediation policy generation, and MTTR telemetry — all exposed via a unified Python FastAPI gateway with an interactive HTML dashboard.

   163→## Frontend Integration Layer
   164→
   165→The FastAPI gateway at port 8000 is the **sole integration point** for any frontend, middleware, or external consumer. All communication follows a clean REST contract:
   166→
   167→```
   168→Frontend / Middleware / External System
   169→        │
   170→        │  HTTP/REST (JSON)
   171→        ▼
   172→┌──────────────────────────────────────┐
   173→│   FastAPI Gateway  (port 8000)        │
   174→│   ┌──────────────────────────────┐   │
   175→│   │ CORS middleware              │   │
   176→│   │ Request validation (Pydantic)│   │
   177→│   │ OpenAPI /docs + /redoc       │   │
   178→│   └──────────┬───────────────────┘   │
   179→│              │                       │
   180→│    ┌─────────┼─────────┐             │
   181→│    ▼         ▼         ▼             │
   182→│ Anonymiser  Auditor  Remediation     │
   183→│ (Python)    (Python) (Python)        │
   184→│              │                       │
   185→│              ▼                       │
   186→│         MTTR Tracker (Go:8080)       │
   187→│         via httpx proxy              │
   188→└──────────────────────────────────────┘
   189→```
   190→
   191→### Integration Patterns
   192→
   193→| Pattern | How | Use Case |
   194→|---------|-----|----------|
   195→| **Direct REST** | Frontend calls `GET/POST /api/v1/*` | Dashboard data, user actions |
   196→| **Python SDK** | `from client import ComplianceSwarmClient` | Backend-to-backend, scripting |
   197→| **MTTR Proxy** | Gateway proxies `/api/v1/mttr/*` → `Go:8080` | Transparent language boundary |
   198→| **CORS** | `Access-Control-Allow-Origin` configurable | SPA, mobile apps |
   199→| **OpenAPI** | Auto-generated at `/docs` | API exploration, codegen |
   200→
   201→### Frontend Middleware Communication Guide
   202→
   203→The gateway is designed to be the **single API contract** between frontend and backend. Middleware layers (message queues, caching, auth) sit between the frontend and this gateway:
   204→
   205→```
   206→Frontend SPA / Mobile
   207→      │
   208→      ▼
   209→API Gateway / Reverse Proxy (Nginx, Caddy, Kong)
   210→      │  • SSL termination
   211→      │  • Rate limiting
   212→      │  • JWT / API key validation
   213→      ▼
   214→FastAPI Gateway (port 8000)
   215→      │  • Request validation
   216→      │  • Tool orchestration
   217→      │  • MTTR proxy to Go
   218→      ▼
   219→PostgreSQL + PostGIS
   220→      │  • Compliance data
   221→      │  • Geospatial queries
   222→      ▼
   223→Golang MTTR Tracker (port 8080)
   224→      │  • Buffered telemetry
   225→      │  • Background goroutine flush
   226→```
   227→
   228→**Key integration points:**
   229→- All 20 routes return consistent JSON with Pydantic-validated schemas
   230→- Error responses follow `{"detail": "..."}` pattern (FastAPI default)
   231→- MTTR routes proxy transparently — the frontend never needs to know about the Golang service
   232→- The Python SDK (`python/client/`) provides typed models for all request/response shapes

   236→## Python Client SDK
   237→
   238→A typed client is included for frontend and integration use:
   239→
   240→```python
   241→from client import ComplianceSwarmClient, ComplianceDomain, RemediationMode
   242→
   243→api = ComplianceSwarmClient(base_url="http://localhost:8000")
   244→
   245→# Scan a manifest for PII
   246→scan = api.scan_manifest({"consignee_name": "John Doe", "consignee_email": "john@ship.com"})
   247→print(f"Found {scan.pii_fields_found} PII fields")
   248→
   249→# Anonymise
   250→result = api.anonymise_manifest(
   251→    manifest_id="BL-SG-001",
   252→    manifest={"consignee_name": "John Doe", "container_id": "MSKU123"},
   253→)
   254→print(result.anonymised_manifest)  # PII replaced with MTS_CONS_xxxx tokens
   255→
   256→# Run an audit
   257→audit = api.run_audit(domain=ComplianceDomain.ENCRYPTION)
   258→print(f"{audit.findings_count} findings from {audit.queries_executed} queries")
   259→
   260→# Generate remediation policies (dry-run)
   261→policies = api.generate_policies(mode=RemediationMode.DRY_RUN)
   262→
   263→# MTTR report
   264→report = api.get_mttr_report()
   265→print(f"Avg MTTR: {report.avg_mttr_hours}h, P95: {report.p95_mttr_hours}h")
   266→
   267→api.close()
   268→```

   381→## Operational Workflow
   382→
   383→See `docs/workflow_diagram.mmd` (Mermaid) or `docs/workflow_diagram.png` (rendered).
   384→
   385→The swarm operates in 6 phases:
   386→
   387→1. **Ingestion** — Raw manifests from FMS/EDI streams
   388→2. **Detection** — PII rule engine classifies fields by jurisdiction
   389→3. **Tokenisation** — HMAC-SHA256 vault replaces PII with deterministic tokens
   390→4. **Audit** — 11 SQL queries detect encryption, customs, and EDI violations
   391→5. **Remediation** — Decision matrix auto-generates masking policies and EDI fixes
   392→6. **Telemetry** — Golang service tracks MTTR across all findings

   396→## Next-Level Improvement Roadmap
   397→
   398→This section outlines how each component can evolve to meet the demands of rapidly changing data landscapes, emerging technologies, expanding data repositories, and operational challenges like extreme weather in special maritime regions.
   399→
   400→### 1. PII Anonymiser — Next Level
   401→
   402→**Current state:** Regex-based field-name matching, 7 rules, 5 jurisdictions, HMAC-SHA256 + Fernet.
   403→
   404→**Evolving data challenges:**
   405→- Shipping manifests increasingly contain unstructured data (remarks, special instructions, free-text hazmat descriptions) where PII is embedded in narrative text rather than labelled fields
   406→- New data repositories — blockchain-based Bills of Lading, electronic sea waybills, and digital twins — introduce PII in non-traditional formats (JSON-LD, CBOR, protobuf serialised payloads)
   407→- Multi-script PII (CJK names, Arabic script, Cyrillic addresses) defeats ASCII-only regex patterns
   408→
   409→**Recommended upgrades:**
   410→
   411→| Upgrade | Description | Impact |
   412→|---------|-------------|--------|
   413→| **ML-based NER layer** | Integrate a lightweight named-entity recognition model (e.g., spaCy with custom maritime NER) alongside regex. The ML model catches PII that field-name heuristics miss, such as names buried in free-text remarks like "Contact John at Maersk for delivery". | 30-40% improvement in free-text PII recall |
   414→| **Multi-script Unicode support** | Extend regex engine with Unicode property classes (`\p{L}`, `\p{N}`) and locale-aware patterns for CJK, Arabic, Devanagari, Cyrillic name/email/phone formats. Add jurisdiction-specific ID formats (China Resident Identity Card 18-digit, India Aadhaar 12-digit, Brazil CPF 11-digit). | Expands coverage to 15+ additional identity document formats |
   415→| **Format-agnostic parser** | Add parsers for JSON-LD, CBOR, protobuf, and Avro manifest payloads. The anonymiser should detect the serialisation format from content headers and apply the same PII rules regardless of encoding. | Supports blockchain eBL, IoT sensor data, digital twin payloads |
   416→| **Context-aware tokenisation** | Not all PII is equal — a container ID like "MSKU1234567" is semi-identifiable but not personally identifying. Implement a risk-scoring layer that grades PII by re-identification difficulty and applies proportionate masking (tokenise high-risk, generalise low-risk). | Reduces over-masking, preserves data utility |
   417→| **Key rotation without re-tokenisation** | Implement key versioning in the HMAC vault so that key rotation creates new tokens without breaking existing token-to-record mappings. Maintain a reverse lookup table (encrypted) for the previous key version during a transition window. | Zero-downtime cryptographic key rotation |
   418→
   419→### 2. EDI SQL Auditor — Next Level
   420→
   421→**Current state:** 11 parametric SQL queries, 5 compliance domains, static query templates.
   422→
   423→**Evolving data challenges:**
   424→- Maritime regulations change frequently — new IMO amendments, EU ETS (Emissions Trading System) requirements for shipping, and emerging carbon reporting mandates mean audit queries must be continuously updated
   425→- New EDI standards and versions (UN/EDIFACT transitions, ANSI X12 evolution) require the auditor to adapt to schema changes without code deployment
   426→- Data repositories are expanding to include port community systems (PCS), single-window customs platforms, and AIS (Automatic Identification System) data feeds
   427→
   428→**Recommended upgrades:**
   429→
   430→| Upgrade | Description | Impact |
   431→|---------|-------------|--------|
   432→| **Pluggable query registry** | Move audit queries from hardcoded Python to a database-backed registry. New queries can be added, modified, or retired via API calls or a configuration UI without redeploying the service. Support versioned queries so regulatory updates create a new version while the old one remains for historical comparison. | Queries update in real-time as regulations change |
   433→| **AIS data compliance audit** | Add audit queries for AIS (Automatic Identification System) data feeds — verify positional data integrity, flag vessels broadcasting spoofed locations, detect data gaps exceeding regulatory thresholds (e.g., SOLAS Chapter V mandatory reporting intervals). | Covers the fastest-growing maritime data source |
   434→| **EU ETS and carbon reporting domain** | Add a 6th compliance domain: **Emissions Reporting**. Audit queries that verify EU ETS reporting completeness, detect missing MRV (Monitoring, Reporting, Verification) data, flag vessels without assigned EU registry numbers, and check carbon credit documentation. | Addresses the 2024+ EU ETS mandate for maritime |
   435→| **Cross-database federation** | The auditor currently runs against a single FMS database. Extend it to federate queries across multiple data sources — the FMS, a port community system, a customs single-window, and an AIS data warehouse — using SQLAlchemy's multi-engine support or a query federation layer. | Unified audit across all maritime data repositories |
   436→| **Anomaly detection** | Add statistical anomaly detection to audit results. Instead of just running deterministic queries, compute baseline distributions (e.g., average transmission encryption rate per partner, typical document turnaround times) and flag statistical outliers as potential compliance risks before they become violations. | Shift from reactive to proactive compliance |
   437→| **Weather-aware audit scheduling** | Integrate meteorological data feeds (NOAA GFS, ECMWF ERA5) to correlate compliance gaps with severe weather events. During hurricanes, typhoons, or polar storms, EDI transmissions and customs filings frequently fail. The auditor should tag weather-affected findings differently and adjust SLA expectations. | Reduces false-positive critical findings by 20-30% |
   438→
   439→### 3. Remediation Generator — Next Level
   440→
   441→**Current state:** Decision matrix with 7 risk categories, 3 execution modes (dry-run/staged/apply), EDI profile updater.
   442→
   443→**Evolving challenges:**
   444→- Remediation is currently one-directional (finding → policy). Real-world compliance requires feedback loops — did the policy actually fix the issue? Is the partner now compliant? Should the policy be retired?
   445→- Special regions (Arctic shipping lanes, piracy zones, sanctioned territories) require different remediation strategies
   446→- The decision matrix is static and cannot learn from past remediation outcomes
   447→
   448→**Recommended upgrades:**
   449→
   450→| Upgrade | Description | Impact |
   451→|---------|-------------|--------|
   452→| **Closed-loop remediation verification** | After a policy is applied, automatically schedule a re-audit after a configurable delay (e.g., 24h for EDI fixes, 72h for partner onboarding changes). If the re-audit still detects the same issue, escalate to a higher severity and notify the compliance officer. | Ensures remediation actually resolves the root cause |
   453→| **Region-aware remediation policies** | Implement a geo-fencing layer using PostGIS that associates trade lanes and port pairs with regional regulatory requirements. Arctic routes (Northern Sea Route) have different customs, environmental, and data sovereignty rules than standard lanes. Sanctioned territories require additional export control checks. The decision matrix selects different remediation actions based on the geographic context of the finding. | Compliant operations in Arctic, sanctioned, and special economic zones |
   454→| **Weather-disruption remediation mode** | When a severe weather event is active in a region, the remediation generator should automatically enter a "weather-hold" mode for affected findings. Instead of generating enforcement policies for EDI failures caused by a hurricane, it should generate "grace-period" policies that document the weather event as a justifiable cause and auto-expire when the weather clears. | Prevents inappropriate enforcement during force majeure |
   455→| **Machine-learned decision matrix** | Train a lightweight model on historical finding → remediation → verification outcomes. The model learns which remediation actions actually work for which risk categories, partner types, and regions. Over time, it replaces the static decision matrix with a probability-ranked set of recommended actions. | Continuously improving remediation accuracy |
   456→| **Multi-party orchestration** | Some findings require coordinated action across multiple parties (carrier, customs broker, port authority). Add a workflow engine that breaks complex findings into sub-tasks, assigns them to different parties, and tracks completion across all parties before marking the finding as remediated. | Handles cross-organisational compliance issues |

   458→### 4. MTTR Tracker (Golang) — Next Level
   459→
   460→**Current state:** Buffered event ingestion, background goroutine flush, avg/P95 metrics, 5 lifecycle phases.
   461→
   462→**Evolving challenges:**
   463→- MTTR metrics are point-in-time snapshots — they don't capture trends, seasonal patterns, or the compounding effect of simultaneous incidents
   464→- Weather events create burst patterns (many findings at once) that distort MTTR — a hurricane affecting 50 vessels simultaneously shouldn't count the same as 50 isolated findings
   465→- Different regions and trade lanes have fundamentally different remediation timelines
   466→
   467→**Recommended upgrades:**
   468→
   469→| Upgrade | Description | Impact |
   470→|---------|-------------|--------|
   471→| **Time-series MTTR analytics** | Store MTTR calculations as time-series data and expose trend endpoints (`/api/v1/mttr/trend?period=90d`). Use Go's excellent concurrency to compute rolling averages, exponential moving averages, and seasonal decomposition. Identify whether MTTR is improving or degrading over time. | Data-driven compliance performance tracking |
   472→| **Weather-correlated MTTR adjustment** | Ingest weather event data (storm tracks, port closures, canal blockages) and correlate with MTTR spikes. The report endpoint should offer a "weather-adjusted MTTR" that excludes time periods affected by force majeure events, giving a more accurate picture of operational MTTR vs. environmental MTTR. | Fair and accurate compliance performance measurement |
   473→| **Regional MTTR breakdown** | Break down MTTR by geographic region, trade lane, or port pair. Arctic routes, trans-Pacific, and intra-Asia lanes have fundamentally different remediation timelines. Expose `/api/v1/mttr/report?region=arctic` for regional analysis. | Identifies regional compliance bottlenecks |
   474→| **Burst detection and clustering** | Implement an algorithm that detects when multiple related findings appear simultaneously (e.g., a partner's EDI system goes down affecting 30 shipments). Cluster these into a single "incident" and track MTTR at the incident level rather than the individual finding level. | Prevents MTTR distortion from correlated failures |
   475→| **Predictive MTTR estimation** | When a new finding is created, estimate its expected MTTR based on historical data for the same risk category, severity, partner, and region. Display this as "predicted resolution: 4.2h" on the dashboard. Uses a simple regression model trained on historical MTTR data — no heavy ML infrastructure required. | Sets realistic expectations, enables proactive resource allocation |
   476→| **Streaming MTTR via Server-Sent Events** | Expose a real-time MTTR feed via SSE (`/api/v1/mttr/stream`). The Golang service pushes MTTR updates as findings progress through lifecycle phases. This enables live dashboards without polling. | Real-time compliance visibility |

   500→| **Gulf of Aden / Red Sea** | Extreme heat (50°C+), piracy risk, Houthi disruptions | Route deviations, partner communication blackouts, sanctioned territory proximity | Sanction screening on route changes, automatic grace-period policies, security-finding escalation |

   559→## Security Considerations
   560→
   561→- **HMAC key** — drives all tokenisation determinism; rotating it invalidates every token. Treat as a root CA key.
   562→- **Fernet keys** — generated per-session by default; for production, rotate via a key management service.
   563→- **Gateway auth** — add API key or JWT middleware before production exposure (especially `apply` mode endpoints).
   564→- **CORS** — currently wildcard; lock to your frontend domain in production.
   565→- **Rate limiting** — not yet implemented; bulk manifest uploads could spike DB writes.
