     1→# Maritime Global Compliance Swarm
     2→
     3→> Autonomous regulatory compliance agent swarm for global maritime freight. Automates GDPR/PII anonymisation, EDI compliance audits, remediation policy generation, MTTR telemetry, finding state machine governance, and event-driven reactive compliance — all exposed via a unified Python FastAPI gateway with an interactive HTML dashboard.

   210→## Frontend Integration Layer
   211→
   212→The FastAPI gateway at port 8000 is the **sole integration point** for any frontend, middleware, or external consumer. All communication follows a clean REST contract:
   213→
   214→```
   215→Frontend / Middleware / External System
   216→        │
   217→        │  HTTP/REST (JSON)
   218→        ▼
   219→┌──────────────────────────────────────┐
   220→│   FastAPI Gateway  (port 8000)        │
   221→│   ┌──────────────────────────────┐   │
   222→│   │ CORS middleware              │   │
   223→│   │ Request validation (Pydantic)│   │
   224→│   │ OpenAPI /docs + /redoc       │   │
   225→│   └──────────┬───────────────────┘   │
   226→│              │                       │
   227→│    ┌─────────┼─────────┐             │
   228→│    ▼         ▼         ▼             │
   229→│ Anonymiser  Auditor  Remediation     │
   230→│ (Python)    (Python) (Python)        │
   231→│              │                       │
   232→│              ▼                       │
   233→│         MTTR Tracker (Go:8080)       │
   234→│         via httpx proxy              │
   235→└──────────────────────────────────────┘
   236→```
   237→
   238→### Integration Patterns
   239→
   240→| Pattern | How | Use Case |
   241→|---------|-----|----------|
   242→| **Direct REST** | Frontend calls `GET/POST /api/v1/*` | Dashboard data, user actions |
   243→| **Python SDK** | `from client import ComplianceSwarmClient` | Backend-to-backend, scripting |
   244→| **MTTR Proxy** | Gateway proxies `/api/v1/mttr/*` → `Go:8080` | Transparent language boundary |
   245→| **CORS** | `Access-Control-Allow-Origin` configurable | SPA, mobile apps |
   246→| **OpenAPI** | Auto-generated at `/docs` | API exploration, codegen |
   247→| **Connectivity Check** | `GET /api/v1/system/connectivity` | Frontend confirms backend health |
   248→
   249→### Frontend Middleware Communication Guide
   250→
   251→The gateway is designed to be the **single API contract** between frontend and backend. Middleware layers (message queues, caching, auth) sit between the frontend and this gateway:
   252→
   253→```
   254→Frontend SPA / Mobile
   255→      │
   256→      ▼
   257→API Gateway / Reverse Proxy (Nginx, Caddy, Kong)
   258→      │  • SSL termination
   259→      │  • Rate limiting
   260→      │  • JWT / API key validation
   261→      ▼
   262→FastAPI Gateway (port 8000)
   263→      │  • Request validation
   264→      │  • Tool orchestration
   265→      │  • MTTR proxy to Go
   266→      ▼
   267→PostgreSQL + PostGIS
   268→      │  • Compliance data
   269→      │  • Geospatial queries
   270→      ▼
   271→Golang MTTR Tracker (port 8080)
   272→      │  • Buffered telemetry
   273→      │  • Background goroutine flush
   274→```
   275→
   276→**Key integration points:**
   277→- All 30+ routes return consistent JSON with Pydantic-validated schemas
   278→- Error responses follow `{"detail": "..."}` pattern (FastAPI default)
   279→- MTTR routes proxy transparently — the frontend never needs to know about the Golang service
   280→- The Python SDK (`python/client/`) provides typed models for all request/response shapes
   281→- **Connectivity endpoint** (`GET /api/v1/system/connectivity`) tests all 10 components with latency measurements — call this first from any frontend to confirm backend communication

   301→## Python Client SDK
   302→
   303→A typed client is included for frontend and integration use:
   304→
   305→```python
   306→from client import ComplianceSwarmClient, ComplianceDomain, RemediationMode
   307→
   308→api = ComplianceSwarmClient(base_url="http://localhost:8000")
   309→
   310→# Scan a manifest for PII
   311→scan = api.scan_manifest({"consignee_name": "John Doe", "consignee_email": "john@ship.com"})
   312→print(f"Found {scan.pii_fields_found} PII fields")
   313→
   314→# Anonymise
   315→result = api.anonymise_manifest(
   316→    manifest_id="BL-SG-001",
   317→    manifest={"consignee_name": "John Doe", "container_id": "MSKU123"},
   318→)
   319→print(result.anonymised_manifest)  # PII replaced with MTS_CONS_xxxx tokens
   320→
   321→# Run an audit
   322→audit = api.run_audit(domain=ComplianceDomain.ENCRYPTION)
   323→print(f"{audit.findings_count} findings from {audit.queries_executed} queries")
   324→
   325→# Generate remediation policies (dry-run)
   326→policies = api.generate_policies(mode=RemediationMode.DRY_RUN)
   327→
   328→# MTTR report
   329→report = api.get_mttr_report()
   330→print(f"Avg MTTR: {report.avg_mttr_hours}h, P95: {report.p95_mttr_hours}h")
   331→
   332→api.close()
   333→```

   455→## Operational Workflow
   456→
   457→See `docs/workflow_diagram.mmd` (Mermaid) or `docs/workflow_diagram.png` (rendered).
   458→
   459→The swarm operates in 8 phases:
   460→
   461→1. **Ingestion** — Raw manifests from FMS/EDI streams
   462→2. **Detection** — PII rule engine + ML NER classifies fields by jurisdiction
   463→3. **Tokenisation** — HMAC-SHA256 vault replaces PII with deterministic tokens
   464→4. **Audit** — 11 SQL queries detect encryption, customs, and EDI violations
   465→5. **State Machine Governance** — Finding lifecycle managed through 10 validated states with guard conditions and timeout SLAs
   466→6. **Event-Driven Reactions** — 7 autonomous rules react to findings (CRITICAL alerts, PII auto-scan, cert checks, timeout escalation)
   467→7. **Remediation** — Decision matrix auto-generates masking policies and EDI fixes
   468→8. **Telemetry** — Golang service tracks MTTR across all findings
   469→
   470→### Finding State Machine
   471→
   472→Every compliance finding follows a validated lifecycle:
   473→
   474→```
   475→DETECTED → TRIAGED → ASSIGNED → IN_REMEDIATION → AWAITING_VERIFICATION → VERIFIED → CLOSED
   476→    │          │           │              │                    │                    │
   477→    │          └── FALSE_POSITIVE     │              │                    └── IN_REMEDIATION (regression)
   478→    │                              └── ESCALATED ←───┘                    │
   479→    │                                  │                                    │
   480→    └────────────────────────── RISK_ACCEPTED ────────────────────── CLOSED
   481→```
   482→
   483→**Key features:**
   484→- **Guard conditions**: CRITICAL findings cannot transition to RISK_ACCEPTED without sign-off
   485→- **Timeout rules**: CRITICAL = 1hr per state, HIGH = 4hr, MEDIUM = 24hr (configurable per state)
   486→- **Auto-escalation**: Timeout breaches automatically transition to ESCALATED via timer actor
   487→- **Audit trail**: Every transition recorded in `finding_transitions` table with trigger, actor, context
   488→- **Legacy bridge**: Maps old 5-state `AuditStatus` to new 10-state `FindingState` for backward compatibility
   489→
   490→### Event-Driven Reactions
   491→
   492→The swarm reacts autonomously to compliance events through 7 built-in rules:
   493→
   494→| Rule | Event | Action |
   495→|------|-------|--------|
   496→| Critical Notification | `finding.created` (CRITICAL) | Emit high-priority alert for immediate assignment |
   497→| PII Auto-Scan | `finding.created` (PII_EXPOSURE) | Queue related manifests for anonymisation scan |
   498→| Cert Renewal Check | `finding.created` (CERT_EXPIRY) | Schedule 24hr cert renewal check |
   499→| Timeout Escalation | `finding.timeout_breach` | Auto-escalate via state machine |
   500→| Verification Reminder | `finding.state_changed` → awaiting_verification | Emit reminder with timeout window |
   501→| Audit Summary | `audit.completed` | Log severity breakdown |
   502→| MTTR Baseline | `finding.created` (CRITICAL/HIGH) | Create MTTR tracking baseline |
   503→
   504→Events use PostgreSQL LISTEN/NOTIFY in production (real-time push) and in-process queue in development.

   508→## Next-Level Improvement Roadmap
   509→
   510→This section outlines how each component can evolve to meet the demands of rapidly changing data landscapes, emerging technologies, expanding data repositories, and operational challenges like extreme weather in special maritime regions.
   511→
   512→### 1. PII Anonymiser — Next Level
   513→
   514→**Current state:** Regex-based field-name matching, 7 rules, 5 jurisdictions, HMAC-SHA256 + Fernet.
   515→
   516→**Evolving data challenges:**
   517→- Shipping manifests increasingly contain unstructured data (remarks, special instructions, free-text hazmat descriptions) where PII is embedded in narrative text rather than labelled fields
   518→- New data repositories — blockchain-based Bills of Lading, electronic sea waybills, and digital twins — introduce PII in non-traditional formats (JSON-LD, CBOR, protobuf serialised payloads)
   519→- Multi-script PII (CJK names, Arabic script, Cyrillic addresses) defeats ASCII-only regex patterns
   520→
   521→**Recommended upgrades:**
   522→
   523→| Upgrade | Description | Impact |
   524→|---------|-------------|--------|
   525→| **ML-based NER layer** | Integrate a lightweight named-entity recognition model (e.g., spaCy with custom maritime NER) alongside regex. The ML model catches PII that field-name heuristics miss, such as names buried in free-text remarks like "Contact John at Maersk for delivery". | 30-40% improvement in free-text PII recall |
   526→| **Multi-script Unicode support** | Extend regex engine with Unicode property classes (`\p{L}`, `\p{N}`) and locale-aware patterns for CJK, Arabic, Devanagari, Cyrillic name/email/phone formats. Add jurisdiction-specific ID formats (China Resident Identity Card 18-digit, India Aadhaar 12-digit, Brazil CPF 11-digit). | Expands coverage to 15+ additional identity document formats |
   527→| **Format-agnostic parser** | Add parsers for JSON-LD, CBOR, protobuf, and Avro manifest payloads. The anonymiser should detect the serialisation format from content headers and apply the same PII rules regardless of encoding. | Supports blockchain eBL, IoT sensor data, digital twin payloads |
   528→| **Context-aware tokenisation** | Not all PII is equal — a container ID like "MSKU1234567" is semi-identifiable but not personally identifying. Implement a risk-scoring layer that grades PII by re-identification difficulty and applies proportionate masking (tokenise high-risk, generalise low-risk). | Reduces over-masking, preserves data utility |
   529→| **Key rotation without re-tokenisation** | Implement key versioning in the HMAC vault so that key rotation creates new tokens without breaking existing token-to-record mappings. Maintain a reverse lookup table (encrypted) for the previous key version during a transition window. | Zero-downtime cryptographic key rotation |
   530→
   531→### 2. EDI SQL Auditor — Next Level
   532→
   533→**Current state:** 11 parametric SQL queries, 5 compliance domains, static query templates.
   534→
   535→**Evolving data challenges:**
   536→- Maritime regulations change frequently — new IMO amendments, EU ETS (Emissions Trading System) requirements for shipping, and emerging carbon reporting mandates mean audit queries must be continuously updated
   537→- New EDI standards and versions (UN/EDIFACT transitions, ANSI X12 evolution) require the auditor to adapt to schema changes without code deployment
   538→- Data repositories are expanding to include port community systems (PCS), single-window customs platforms, and AIS (Automatic Identification System) data feeds
   539→
   540→**Recommended upgrades:**
   541→
   542→| Upgrade | Description | Impact |
   543→|---------|-------------|--------|
   544→| **Pluggable query registry** | Move audit queries from hardcoded Python to a database-backed registry. New queries can be added, modified, or retired via API calls or a configuration UI without redeploying the service. Support versioned queries so regulatory updates create a new version while the old one remains for historical comparison. | Queries update in real-time as regulations change |
   545→| **AIS data compliance audit** | Add audit queries for AIS (Automatic Identification System) data feeds — verify positional data integrity, flag vessels broadcasting spoofed locations, detect data gaps exceeding regulatory thresholds (e.g., SOLAS Chapter V mandatory reporting intervals). | Covers the fastest-growing maritime data source |
   546→| **EU ETS and carbon reporting domain** | Add a 6th compliance domain: **Emissions Reporting**. Audit queries that verify EU ETS reporting completeness, detect missing MRV (Monitoring, Reporting, Verification) data, flag vessels without assigned EU registry numbers, and check carbon credit documentation. | Addresses the 2024+ EU ETS mandate for maritime |
   547→| **Cross-database federation** | The auditor currently runs against a single FMS database. Extend it to federate queries across multiple data sources — the FMS, a port community system, a customs single-window, and an AIS data warehouse — using SQLAlchemy's multi-engine support or a query federation layer. | Unified audit across all maritime data repositories |
   548→| **Anomaly detection** | Add statistical anomaly detection to audit results. Instead of just running deterministic queries, compute baseline distributions (e.g., average transmission encryption rate per partner, typical document turnaround times) and flag statistical outliers as potential compliance risks before they become violations. | Shift from reactive to proactive compliance |
   549→| **Weather-aware audit scheduling** | Integrate meteorological data feeds (NOAA GFS, ECMWF ERA5) to correlate compliance gaps with severe weather events. During hurricanes, typhoons, or polar storms, EDI transmissions and customs filings frequently fail. The auditor should tag weather-affected findings differently and adjust SLA expectations. | Reduces false-positive critical findings by 20-30% |
   550→
   551→### 3. Remediation Generator — Next Level
   552→
   553→**Current state:** Decision matrix with 7 risk categories, 3 execution modes (dry-run/staged/apply), EDI profile updater.
   554→
   555→**Evolving challenges:**
   556→- Remediation is currently one-directional (finding → policy). Real-world compliance requires feedback loops — did the policy actually fix the issue? Is the partner now compliant? Should the policy be retired?
   557→- Special regions (Arctic shipping lanes, piracy zones, sanctioned territories) require different remediation strategies
   558→- The decision matrix is static and cannot learn from past remediation outcomes
   559→
   560→**Recommended upgrades:**
   561→
   562→| Upgrade | Description | Impact |
   563→|---------|-------------|--------|
   564→| **Closed-loop remediation verification** | After a policy is applied, automatically schedule a re-audit after a configurable delay (e.g., 24h for EDI fixes, 72h for partner onboarding changes). If the re-audit still detects the same issue, escalate to a higher severity and notify the compliance officer. | Ensures remediation actually resolves the root cause |
   565→| **Region-aware remediation policies** | Implement a geo-fencing layer using PostGIS that associates trade lanes and port pairs with regional regulatory requirements. Arctic routes (Northern Sea Route) have different customs, environmental, and data sovereignty rules than standard lanes. Sanctioned territories require additional export control checks. The decision matrix selects different remediation actions based on the geographic context of the finding. | Compliant operations in Arctic, sanctioned, and special economic zones |
   566→| **Weather-disruption remediation mode** | When a severe weather event is active in a region, the remediation generator should automatically enter a "weather-hold" mode for affected findings. Instead of generating enforcement policies for EDI failures caused by a hurricane, it should generate "grace-period" policies that document the weather event as a justifiable cause and auto-expire when the weather clears. | Prevents inappropriate enforcement during force majeure |
   567→| **Machine-learned decision matrix** | Train a lightweight model on historical finding → remediation → verification outcomes. The model learns which remediation actions actually work for which risk categories, partner types, and regions. Over time, it replaces the static decision matrix with a probability-ranked set of recommended actions. | Continuously improving remediation accuracy |
   568→| **Multi-party orchestration** | Some findings require coordinated action across multiple parties (carrier, customs broker, port authority). Add a workflow engine that breaks complex findings into sub-tasks, assigns them to different parties, and tracks completion across all parties before marking the finding as remediated. | Handles cross-organisational compliance issues |
   569→
   570→### 4. MTTR Tracker (Golang) — Next Level
   571→
   572→**Current state:** Buffered event ingestion, background goroutine flush, avg/P95 metrics, 5 lifecycle phases.
   573→
   574→**Evolving challenges:**
   575→- MTTR metrics are point-in-time snapshots — they don't capture trends, seasonal patterns, or the compounding effect of simultaneous incidents
   576→- Weather events create burst patterns (many findings at once) that distort MTTR — a hurricane affecting 50 vessels simultaneously shouldn't count the same as 50 isolated findings
   577→- Different regions and trade lanes have fundamentally different remediation timelines
   578→
   579→**Recommended upgrades:**
   580→
   581→| Upgrade | Description | Impact |
   582→|---------|-------------|--------|
   583→| **Time-series MTTR analytics** | Store MTTR calculations as time-series data and expose trend endpoints (`/api/v1/mttr/trend?period=90d`). Use Go's excellent concurrency to compute rolling averages, exponential moving averages, and seasonal decomposition. Identify whether MTTR is improving or degrading over time. | Data-driven compliance performance tracking |
   584→| **Weather-correlated MTTR adjustment** | Ingest weather event data (storm tracks, port closures, canal blockages) and correlate with MTTR spikes. The report endpoint should offer a "weather-adjusted MTTR" that excludes time periods affected by force majeure events, giving a more accurate picture of operational MTTR vs. environmental MTTR. | Fair and accurate compliance performance measurement |
   585→| **Regional MTTR breakdown** | Break down MTTR by geographic region, trade lane, or port pair. Arctic routes, trans-Pacific, and intra-Asia lanes have fundamentally different remediation timelines. Expose `/api/v1/mttr/report?region=arctic` for regional analysis. | Identifies regional compliance bottlenecks |
   586→| **Burst detection and clustering** | Implement an algorithm that detects when multiple related findings appear simultaneously (e.g., a partner's EDI system goes down affecting 30 shipments). Cluster these into a single "incident" and track MTTR at the incident level rather than the individual finding level. | Prevents MTTR distortion from correlated failures |
   587→| **Predictive MTTR estimation** | When a new finding is created, estimate its expected MTTR based on historical data for the same risk category, severity, partner, and region. Display this as "predicted resolution: 4.2h" on the dashboard. Uses a simple regression model trained on historical MTTR data — no heavy ML infrastructure required. | Sets realistic expectations, enables proactive resource allocation |
   588→| **Streaming MTTR via Server-Sent Events** | Expose a real-time MTTR feed via SSE (`/api/v1/mttr/stream`). The Golang service pushes MTTR updates as findings progress through lifecycle phases. This enables live dashboards without polling. | Real-time compliance visibility |

   671→## Security Considerations
   672→
   673→- **HMAC key** — drives all tokenisation determinism; rotating it invalidates every token. Treat as a root CA key.
   674→- **Fernet keys** — generated per-session by default; for production, rotate via a key management service.
   675→- **Gateway auth** — add API key or JWT middleware before production exposure (especially `apply` mode endpoints).
   676→- **CORS** — currently wildcard; lock to your frontend domain in production.
   677→- **Rate limiting** — not yet implemented; bulk manifest uploads could spike DB writes.
