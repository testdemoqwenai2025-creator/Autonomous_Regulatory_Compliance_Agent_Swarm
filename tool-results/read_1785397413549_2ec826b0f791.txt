     1→# Skill: Global Maritime Data Governance & Privacy Swarm
     2→
     3→## Overview
     4→
     5→Autonomous regulatory compliance agent swarm for global maritime freight operations. The swarm automates GDPR/PII anonymisation, EDI compliance auditing, remediation policy generation, and MTTR telemetry tracking across five international jurisdictions. Designed to evolve with emerging regulations, expanding data repositories, satellite AIS feeds, and the unique challenges of extreme weather and special maritime regions.
     6→
     7→## When to Use This Skill
     8→
     9→- Building compliance automation for maritime logistics, shipping, or freight forwarding
    10→- Implementing PII anonymisation pipelines for Bills of Lading, manifests, or customs declarations
    11→- Auditing EDI connections (EDIFACT, ANSI X12, BAPLIE, VGM) for encryption and format compliance
    12→- Generating automated remediation policies from audit findings
    13→- Tracking Mean Time To Remediate (MTTR) for compliance incidents
    14→- Multi-jurisdiction data governance (GDPR, CCPA, LGPD, PDPA, PIPA)
    15→- Weather-aware compliance operations in extreme maritime environments
    16→- Integrating compliance across diverse maritime data repositories (AIS, PCS, IoT, blockchain eBL)
    17→- Satellite-based vessel tracking compliance and route deviation detection
    18→- Carbon emissions reporting compliance (EU ETS, IMO DCS, MRV)

    22→## Current Capabilities (v3.0)
    23→
    24→### 1. Manifest PII Anonymiser (Python)
    25→
    26→- **HMAC-SHA256 deterministic tokenisation** — produces consistent tokens for the same input across runs, enabling cross-referencing without exposing original data
    27→- **Fernet symmetric encryption** — reversible pseudonymisation for customs DPA-covered use cases (AES-128-CBC + HMAC-SHA256)
    28→- **Multi-jurisdiction PII rules** — 7 default rules covering consignee identity, shipper identity, contact info, government IDs, and financial IDs
    29→- **Free-text PII scanning** — regex-based detection of emails, phone numbers, passport numbers, and tax IDs embedded in free-text fields
    30→- **ML NER detection** — spaCy-based named entity recognition for PII in unstructured free-text (remarks, special instructions, hazmat descriptions)
    31→- **Six masking actions** — tokenise, redact, generalise (date granularity), pseudonymise, encrypt, truncate
    32→- **Token format** — `{PREFIX}_{CATEGORY}_{HMAC_TRUNCATED}` (e.g., `MTS_CONS_a3f8c1e9b2d4`)
    33→
    34→### 2. Logistics EDI SQL Auditor (Python)
    35→
    36→- **11 parametric SQL audit queries** across 5 compliance domains
    37→- **Domain: Encryption** (3 queries) — unencrypted EDI transmissions, FTP file transfers, expired TLS certificates
    38→- **Domain: Customs Documentation** (3 queries) — missing customs declarations, missing VGM, expiring dangerous goods docs
    39→- **Domain: EDI Format** (2 queries) — failed validation messages, orphaned references
    40→- **Domain: Data Retention** (2 queries) — PII past retention period, unanonymised historical manifests
    41→- **Domain: Access Control** (1 query) — excessive user permissions
    42→- **Pluggable query registry** — database-backed, versioned queries updatable via API without redeployment
    43→- **Finding persistence** — all results stored as `AuditFinding` records with severity, risk category, and evidence samples
    44→- **EDI profile scanning** — checks each partner connection for encryption status and TLS version
    45→
    46→### 3. Remediation Route Generator (Python)
    47→
    48→- **Decision matrix** — maps 7 risk categories to recommended policy actions automatically
    49→- **Three execution modes** — dry-run (propose only), staged (persist as disabled), apply (persist and enable)
    50→- **Field category inference** — infers PII category from field names when evidence is ambiguous
    51→- **EDI profile updater** — enforces TLS 1.3 and enables encryption on non-compliant partner connections
    52→- **Finding status tracking** — marks findings as in-progress or remediated when policies are generated
    53→
    54→### 4. Telemetry MTTR Tracker (Golang)
    55→
    56→- **Buffered event ingestion** — in-memory buffer with configurable flush interval (default 10s)
    57→- **Background goroutine** — non-blocking writes to the database
    58→- **Ten lifecycle phases** — aligned with Python FindingState: identified, triaged, assigned, in_progress, awaiting_verification, resolved, verified, escalated, risk_accepted, closed, false_positive
    59→- **MTTR calculation** — average and P95 metrics, broken down by severity and risk category; accepts both "resolved" and "verified" as MTTR end points
    60→- **SQLite (dev) / PostgreSQL (prod)** — driver-agnostic via configuration swap
    61→- **HTTP API** — 6 endpoints including `/api/v1/events/sm` for receiving state machine transition payloads
    62→- **Phase mapping** — `FindingStateToPhase` map translates all 10 Python FindingState values to Go EventPhase constants
    63→
    64→### 5. Finding State Machine (Python)
    65→
    66→- **10 states** — DETECTED, TRIAGED, ASSIGNED, IN_REMEDIATION, AWAITING_VERIFICATION, VERIFIED, CLOSED, ESCALATED, RISK_ACCEPTED, FALSE_POSITIVE
    67→- **20 transitions** — each with trigger, actor, guard conditions, timeout rules, and context payloads
    68→- **7 trigger types** — manual_triage, manual_assign, remediation_submitted, verification_passed, verification_failed, auto_escalate_timeout, manual_close, risk_accept, mark_false_positive
    69→- **Guard conditions** — e.g., CLOSURE requires no open remediation tasks; ESCALATION requires sign-off for CRITICAL findings
    70→- **Timeout SLAs** — per-severity auto-escalation (CRITICAL: 1h detected/triaged, 4h assigned, 8h remediation; HIGH: 4h/8h/24h; MEDIUM: 24h/48h/72h)
    71→- **Callback bridge** — registered callback on every successful transition auto-emits FINDING_STATE_CHANGED event to the event bus
    72→- **Go MTTR bridge** — async HTTP POST forwards every transition to Go service via `map_go_phase()` static method
    73→- **Full audit trail** — every transition persisted to `finding_transitions` table with before/after state, trigger, actor, context payload, and auto-escalation flag
    74→- **Manual timeout check** — `POST /api/v1/state-machine/timeout-check` endpoint scans all open findings and auto-escalates SLA breaches
    75→
    76→### 6. Event Bus (Python)
    77→
    78→- **Database-backed event store** — all events persisted to `event_log` table with full metadata
    79→- **PG LISTEN/NOTIFY fallback** — uses PostgreSQL real-time notifications when available; falls back to in-process queue for SQLite
    80→- **Background consumer loop** — processes queued events and dispatches to subscribers
    81→- **Subscriber API** — register handlers for specific event types with optional correlation ID filtering
    82→- **Statistics endpoint** — `GET /api/v1/events/stats` returns total events, processed count, queue depth, transport type, subscriber count
    83→- **Event log query** — `GET /api/v1/events` returns recent events with filtering
    84→- **Manual publish** — `POST /api/v1/events/publish` for testing and external integration
    85→
    86→### 7. Reaction Engine (Python)
    87→
    88→- **7 built-in reaction rules** with conditions and actions:
    89→  1. `react_critical_notification` — CRITICAL findings trigger EDI partner notification and auto-escalation
    90→  2. `react_pii_auto_scan` — PII exposure findings trigger automatic anonymisation scan
    91→  3. `react_cert_expiry_check` — certificate expiry findings trigger compliance audit re-run
    92→  4. `react_timeout_escalation` — timeout events trigger escalation with SLA context
    93→  5. `react_remediation_verification` — remediation completion triggers verification workflow
    94→  6. `react_audit_summary` — audit completion triggers summary report generation
    95→  7. `react_mttr_baseline` — new finding creation triggers MTTR baseline establishment
    96→- **Conditional execution** — each rule evaluates event type, severity, risk category, and payload fields before firing
    97→- **Toggle API** — `PUT /api/v1/reactions/rules/{rule_id}/toggle` enables or disables individual rules at runtime
    98→- **Statistics endpoint** — `GET /api/v1/reactions/stats` returns enabled count, total actions executed, and per-rule action counts
    99→- **Reaction log** — `GET /api/v1/reactions/log` shows recent reaction activity with full context

   101→### 8. Composite Risk Scoring Engine (Python) ★ NEW in v3.0
   102→
   103→- **5-dimensional weighted model** — CRS = 0.30*S_sev + 0.20*S_jur + 0.20*S_sens + 0.15*S_exp + 0.15*S_urg
   104→- **Severity sub-score** — direct lookup (CRITICAL=1.0, HIGH=0.8, MEDIUM=0.5, LOW=0.3, INFO=0.1)
   105→- **Jurisdiction sub-score** — enforcement rigour weighting (GDPR=1.0, CCPA=0.85, LGPD=0.70, PIPA=0.65, PDPA=0.50)
   106→- **Data sensitivity sub-score** — 8 levels from special_category=1.0 to operational=0.25
   107→- **Exposure breadth sub-score** — logarithmic scaling combining record count, partner count, and jurisdiction count
   108→- **Temporal urgency sub-score** — age-based ramping (0-72h), SLA deadline proximity, state-dependent reduction
   109→- **Risk level mapping** — CRS >= 0.80 CRITICAL, >= 0.60 HIGH, >= 0.40 MEDIUM, >= 0.20 LOW, < 0.20 INFO
   110→- **ORM convenience** — `score_finding(audit_finding)` method for direct scoring from database objects

   229→### Supported Region Profiles
   230→
   231→| Region | Weather Risks | Compliance Adjustments |
   232→|--------|--------------|----------------------|
   233→| **Arctic (Northern Sea Route)** | Sea ice, polar lows, -40C, satellite-only comms | Extended SLAs, ice-route customs pre-clearance, satellite-optimised EDI retry |
   234→| **Gulf of Aden / Red Sea** | Extreme heat 50C+, piracy, Houthi disruptions | Sanction screening on route changes, automatic grace-period, security escalation |
   235→| **Bay of Bengal** | Cyclone season Apr-Dec, monsoon flooding, port closures | Weather-hold mode, bulk VGM re-submission, port-closure event correlation |
   236→| **Caribbean / Gulf of Mexico** | Hurricane season Jun-Nov, storm surge, port evacuations | Burst-mode MTTR clustering, insurance doc auto-gen, regional weather-adjusted SLAs |
   237→| **Strait of Malacca** | Tropical thunderstorms, high traffic, AIS congestion | Deduplication audit, AIS gap detection, high-throughput message queue |
   238→| **English Channel / North Sea** | Fog, rough seas, wind farm AIS interference | Container-loss incident templates, hazmat exposure audit, weather-correlated MTTR |
   239→
   240→### Weather Integration Architecture
   241→
   242→1. **Weather Ingestion Service** — Polls NOAA GFS, ECMWF ERA5, and commercial APIs every 15 minutes
   243→2. **Marine Zone Forecast Storage** — Weather data stored in PostgreSQL with PostGIS spatial indexing
   244→3. **Compliance Event Bus** — Weather events (PORT_CLOSURE, STORM_TRACK, CANAL_BLOCKAGE) join with compliance events via Redis Streams
   245→4. **Downstream Consumers** — Auditor tags findings with weather context, Remediation enters weather-hold mode, MTTR excludes force majeure periods
   246→
   247→### Weather-Aware Compliance Patterns
   248→
   249→| Pattern | Trigger | System Response |
   250→|---------|---------|-----------------|
   251→| **Weather hold** | Active storm within 200nm of affected port | Pause remediation SLA clocks, generate grace-period policies |
   252→| **Weather-adjusted MTTR** | Finding created during active weather event | Exclude weather duration from MTTR calculation |
   253→| **Bulk re-filing** | Port reopens after closure | Auto-generate customs re-filing tasks for affected shipments |
   254→| **Route deviation audit** | Vessel deviates from declared route | Cross-reference with weather/piracy/sanction events to classify deviation type |
   255→| **Environmental compliance** | Temperature excursion in cold-chain container | Generate hazmat compliance finding, notify food/pharma regulatory contacts |

   301→## Database Schema
   302→
   303→9 SQLAlchemy ORM tables:
   304→
   305→1. `anonymisation_records` — audit trail for every PII field anonymised
   306→2. `masking_policies` — field-level masking rules with GDPR article references
   307→3. `audit_findings` — compliance issues found by the EDI auditor
   308→4. `edi_connection_profiles` — partner EDI connection configurations
   309→5. `mttr_events` — telemetry events tracking finding lifecycle phases
   310→6. `compliance_reports` — periodic compliance summary reports
   311→7. `finding_transitions` — complete audit trail of every state machine transition (from_state, to_state, trigger, actor, context_payload, auto_escalated, timeout_hours)
   312→8. `event_log` — immutable event store for all system events (event_type, source, correlation_id, payload, created_at)
   313→9. `audit_query_registry` — pluggable, versioned audit queries (domain, name, sql_template, parameters, version, is_active)
   314→
   315→7 Enum types:
   316→
   317→- `FindingState` — detected, triaged, assigned, in_remediation, awaiting_verification, verified, closed, escalated, risk_accepted, false_positive
   318→- `PIIFieldCategory` — consignee_identity, shipper_identity, contact_info, financial_id, government_id, location
   319→- `AuditSeverity` — critical, high, medium, low, info
   320→- `AuditStatus` — open, in_progress, remediated, accepted_risk, false_positive
   321→- `EDIStandard` — EDIFACT, ANSI_X12, BAPLIE, VGM, COPARN, IFTMBC, CUSTOMS
   322→- `PolicyAction` — tokenise, redact, generalise, pseudonymise, encrypt, truncate
   323→- `RiskCategory` — pii_exposure, unencrypted_transmission, missing_customs_doc, edi_non_compliance, data_retention_violation, access_control_breach, cert_expiry

   414→## Security Considerations
   415→
   416→- **HMAC key** — drives all tokenisation determinism; rotating it invalidates every token. Treat as a root CA key.
   417→- **Fernet keys** — generated per-session by default; for production, rotate via a key management service.
   418→- **Gateway auth** — JWT/API key middleware available in pipeline (enable via SwarmConfig for production).
   419→- **CORS** — currently wildcard; lock to your frontend domain in production.
   420→- **Rate limiting** — token-bucket middleware (100 req/60s, 150 burst); production should use Redis-backed distributed limiting.
   421→- **Audit logging** — structured audit log middleware in pipeline captures every request with request ID, user, timestamp, and response status.
